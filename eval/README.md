# O2: исходные запросы У2 и предложенный корпус из 50 сценариев

**Статус новых 40 сценариев — `proposed/not_team_approved`.** Мы подготовили их
сами для проверки интеграции. Они не предоставлены другими участниками и не
считаются утверждёнными владельцами зон. Обозначения `u1/u3/u4/u5` — предложенное
разбиение покрытия, которое ещё нужно согласовать с командой и R6.

## Что проверяется сейчас

| Файл | Количество | Покрытие |
| --- | ---: | --- |
| `cases/u1.yaml` | 10 новых | Бриф, уточнения, явные и выведенные значения, даты, семья, животные, поезд. |
| `cases/u2.yaml` | 10 исходных | Источники данных, климат/визы, бюджет, отмена, местные даты, D8 и провокация. Исходные критерии сохранены. |
| `cases/u3.yaml` | 10 новых | Пересборка без потери группы/маршрута, бюджет, звёзды, прямые рейсы, возвратность и изменение класса поезда. |
| `cases/u4.yaml` | 10 новых | SSE, арифметика компонентов, ночной прилёт, `null`, ошибки источника, удаление и изоляция сессий. |
| `cases/u5.yaml` | 10 новых | Демо-checkout, состав группы, запрет подмены суммы, подтверждения, отказ оплаты, повтор, ваучер и календарь. |

`app/submission_eval.py` выполняет настоящие HTTP-запросы к приложению через
TestClient, разбирает SSE и читает состояние `/api/session`. Оформление проверяется
через реальные маршруты `/api/checkout`, с отдельной временной SQLite-базой.
Имена и даты рождения путешественников вымышлены и помечены `Demo Fictional`.
Приватная рабочая база заказов не используется.

Это проверка детерминированных правил и backend-инвариантов: `LLM_PROVIDER=fake`,
реальные реализации инструментов с **синтетическими** коммерческими данными.
Внешние HTTP/TCP-соединения запрещены; `.env` и ключи не читаются. Она не измеряет
качество будущей языковой модели, не проверяет свежие предложения поставщиков
и не заменяет человеческие проходы через UI по D9.

Часть сценариев явно использует ограниченные fixtures:
`missing_transfer`, `unknown_hotel_rules`, `unknown_destination_facts`,
`flight_source_error`. Они изменяют типизированный результат инструмента или
имитируют его отказ; планировщик, маршрутизация, HTTP/SSE и checkout остаются
настоящими. Fixture сохраняется в отчёте. Ответ под текст конкретного запроса
не подставляется.

## Запуск и наблюдавшийся результат

Из корня репозитория:

```sh
uv run --project backend python scripts/run_submission_eval.py \
  --today 2026-10-28 --output /tmp/submission-eval.json
```

Для проверки только предложенных 40 сценариев добавьте `--proposed-only`.
Часы агента явно фиксируются параметром `--today`; поэтому результат можно
повторить после даты проведения проверки. Продуктовый поиск по прошедшим датам
этим не объявляется допустимым.

На 28.10.2026: **40/40 предложенных сценариев проходят**, исходный У2 — **9/10**,
вместе **49 passed / 1 failed / 0 blocked**. Общая команда намеренно возвращает
код 1: исходный `u2-03` остаётся несоответствием. Только `--proposed-only`
завершается кодом 0 при успешном результате всех новых сценариев.

`u2-03` требует непустые семейные варианты до 150 000 ₽, но минимальные известные
расходы на этих синтетических данных — 153 378 ₽. Агент корректно отказывает;
исходник не исправлен ради зелёного отчёта. Положительный HTTP-контроль при 170к
и разбивка суммы описаны в [проверке выполнимости](reports/u2-budget-feasibility.md).
Для изменения исходного бюджета или превращения сценария в отрицательный
нужно отдельное явное согласование критерия.

Отчёт хранит исходные тексты/контекст/действия, фактические HTTP-ответы,
SSE-трассы, состояния, проверки свойств, fixtures, длительности, SHA256 кода,
данных и всех пяти файлов корпуса. Новые и исходные сценарии считаются отдельно.
`failed` означает наблюдаемое несоответствие, `blocked` — сбой выполнения проверки;
оба статуса сохраняются, а не превращаются в успешный результат.

## Правила интерпретации и дальнейшее согласование

`all` требует непустого списка и проверки каждого элемента. Отсутствующее поле
отличается от явно переданного `null`; неизвестная цена не становится нулём,
неизвестный визовый режим — безвизовым, неизвестный дедлайн — придуманной датой.
`price_scope` описывает состав суммы, а её расчёт отдельно сверяется по компонентам.
Follow-up `u2-08` использует фактически найденный отель и выбранный вариант.

Схема `id/text/checks/tags` остаётся предложением для #11, не утверждённым O1
TripState. Владельцам зон и R6 нужно подтвердить покрытие и критерии либо
заменить предложенные сценарии своими. После подключения командной модели
нужен отдельный прогон с её настройками и собственными метриками качества.

Проверенный backend уже прошёл пять автоматических проходов до демонстрационных
документов. Пять человеческих проходов через общий UI по ≤300 секунд остаются
отдельным критерием: см. [сценарий D9](../docs/demo.md) и `eval/demo-runs.json`.
