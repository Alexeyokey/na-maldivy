# Orchestrator и реестр данных

Изменения подготовлены относительно ветки `orchestrator` (`b6f7bbf`). Это отдельный PR с исправлениями агента;
реализации D2–D8 сюда не копируются. Исходный PR агента #49 закрыт без слияния, поэтому база этого PR —
`orchestrator`, а не `main`. После интеграции агента базу нужно перевести на `main`.

## Зависимости и воспроизводимая проверка

Исходный orchestrator поддерживает только заглушки. Для `TOOLS_MODE=real` нужны реестр #58 и реализации
D5 #54, D3 #55, D4 #56, D2 #57, D8 #59, D6 #60; для проверки профилей D7 нужен #61.
S3/S4/S5 уже входят в общую базу. Подготовка демо #62 не является зависимостью выполнения агента.

Для проверки собрана отдельная локальная ветка `codex/orchestrator-integration-check`: объединённые
ветки данных + исходный `orchestrator` + этот PR. В реализации агента остаются только его изменения.

В checkout с этими зависимостями:

```bash
bash scripts/check_orchestrator_registry.sh
```

Скрипт сначала проверяет наличие модулей D2/D3/D5/D6/D7/D8 и всех шести реальных адаптеров, затем запускает
регрессии агента и интеграцию через HTTP/SSE. При отсутствии зависимостей он завершается ошибкой,
а не выдаёт пропущенные тесты за успешную интеграцию. Сеть и внешняя LLM не используются.

Полная локальная проверка:

```bash
cd backend
uv run ruff check .
uv run ruff format --check .
uv run pytest
```

На самостоятельной ветке агента интеграционный модуль явно пропускается, потому что адаптеров ещё нет.
В объединённой ветке все его проверки выполняются. Docker-smoke отдельно требует работающего Docker.

## Что изменено

- D5: неизвестные цена, длительность, климат и визовое условие сохраняются как `null`. Они не участвуют
  в арифметике как числа и не превращаются в ноль/«без визы». Неизвестное не удовлетворяет явно заданному
  ограничению. При снятии бюджета для справочных карточек агент говорит, что бюджет не проверен.
- Код выбранного направления D5 больше не ограничивается тремя маршрутами авиаданных. Название карточки
  берётся из `Place.name`. Отсутствие рейсов вне seed-направлений сообщается честно, без генерации предложений.
- Фактическая длительность обоих рейсов проверяется в UTC по ограничению из брифа. Явно указанный год
  сохраняется; прошлые даты отклоняются, а не переносятся молча на следующий год.
- Багаж обоих рейсов входит в расчёт ровно один раз. Варианты, где даже известные расходы превышают бюджет,
  не выдаются как подходящие. Календарь выбирает дату по доступной цене перелёта в одну сторону;
  это не доказательство экономии всей поездки.
- S4: следующий доступный рейс трансфера сохраняется даже при `available=false`. Ожидание до утра
  попадает в таймлайн S3 и валидатор S5. Проверяется сценарий Мале 23:40 → гидросамолёт 06:00.
- Возвратность отеля имеет три состояния: `true` / `false` / `null`. `true` не обещает бесплатную отмену.
  При обязательном возвратном тарифе или минимуме звёзд неизвестные значения не проходят фильтр.
- Сбой источника отличается от пустой выдачи; сбой валидатора больше не означает «проблем нет».
  Ошибки источников в SSE не раскрывают локальные пути. Подмена реальных адаптеров заглушками не выполняется.
- Сохраняются профиль D7 в карточке отеля и предложения S5 `Fix.patch` / `price_estimated` в событиях.
- Запрос поезда идёт в D6: маршрут Петербург ↔ Москва, точная дата, класс мест и вся группа. Изменение класса
  пересчитывает выдачу. Для поездов возвращается `options.kind=trains`, этап `trains_shown`;
  оформления железнодорожных билетов здесь нет.

## Цена и подтверждение: границы результата

В пакете оцениваются **перелёты туда и обратно + багаж + отель + трансфер из аэропорта**.
Обратный трансфер, виза и прочие обязательные доплаты ещё не рассчитаны. Это не полная корзина поездки.

Карточка содержит:

| Поле | Значение |
| --- | --- |
| `price_scope` | `round_trip_flights_baggage_hotel_arrival_transfer` |
| `total_rub` | Сумма перечисленных компонентов; `null`, если нет трансфера из аэропорта |
| `known_total_rub` | Только известные расходы; нельзя выдавать за полную цену |
| `unpriced_components` | `return_transfer`, `visa_and_other_required_extras` |
| `validation_status` | `checked` или `failed`; наличие проблем отдельно в `issues` |
| `can_confirm` | Разрешена ли имитация подтверждения выбранного варианта |

При неполной оценке перечисленных компонентов, сбое проверки, критической проблеме или неподтверждённых
правилах отеля для детей/питомца имитация подтверждения блокируется. Демо-бронь — это проверка последовательности
выбор → подтверждение, без списания денег и создания заказа. Промпт и шаблоны объясняют границы оценки.

Для интерфейса: `total_rub` теперь nullable; нельзя форматировать его без проверки. `known_total_rub` —
не замена полной цене. Неактивное подтверждение определяется `can_confirm`; причины находятся в `risks`/`issues`.
Для `trains` нужна отдельная карточка или текстовый ответ, без кнопки оформления.

## Что доказывают тесты

Регрессии проверяют nullable-поля, смешанные/нулевые значения, обязательные фильтры, ошибки источников,
неполную цену и блокировку подтверждения, багаж, календарь, год даты и переходы поиска поездов.
Интеграция создаёт реестр через `create_tools(Settings(tools_mode="real"))`, проверяет все три направления,
профили D7, идентификаторы OSM ↔ S4, ночное ожидание и HTTP/SSE до имитации бронирования.

`real` здесь означает реализацию адаптеров с локальными наборами данных, а не живую коммерческую выдачу.
Эти проверки не доказывают доступность провайдеров, реальное наличие билетов/номеров или качество живой LLM.
Полноценная корзина, R1/R2/R3/R4 и согласование событий с UI остаются отдельной интеграционной работой.

## Нужны ли ключи и настоящий LLM-прогон

В [D2 #8](https://github.com/ostrovok-hackathon-2026/na-maldivy/issues/8) предусмотрены токен Aviasales,
проверка возможностей/лимитов API и кэш D4. В [D6 #30](https://github.com/ostrovok-hackathon-2026/na-maldivy/issues/30)
предусмотрены ключ Яндекс Расписаний и расписание через кэш D4. Чтобы назвать эти интеграции проверенными,
нужны успешные вызовы с ключами и сохранённое обезличенное подтверждение результата. Моки и локальный replay
не заменяют такую проверку. Aviasales Data API даёт кэш поисковых цен, а не гарантированное наличие для брони.

В [D7 #31](https://github.com/ostrovok-hackathon-2026/na-maldivy/issues/31) указаны отзывы, заранее
сгенерированные моделью, и извлечение аспектов моделью. Текущий шаблонный набор и лексический baseline
подтверждают структуру профилей и счётчики, но не выполнение модельной части. Нужен настоящий прогон
и проверка цитат/упоминаний; модель может быть локальной или через совместимого провайдера.

Во всех трёх issue подробности обозначены как предложение, а не жёсткое ТЗ. Поэтому автономное демо допустимо
показывать с честной маркировкой синтетики; для закрытия объёма с API/LLM нужна соответствующая проверка
либо явное согласование сокращённого объёма. Это вывод из задач проекта, не утверждение об отдельных правилах
оценки хакатона. В рамках этого PR живые API-вызовы и модельный прогон D7 не выполнялись.
