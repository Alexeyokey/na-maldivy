# D6: Петербург ↔ Москва

`TrainTool` реализует D1 search_trains для LED ↔ MOW, алиас SVO → MOW.
Точки — вокзалы с kind=city, а не координаты Пулково/Шереметьево. Четыре класса:
seated/platzkart/coupe/sv. Есть ночной переход даты, дневной seated-вариант и
модель RUB за всю группу: расстояние × ставка класса × сезон × тип поезда,
затем число мест и отдельная модельная доплата за животное. Все люди считаются
занимающими место; детские скидки и право провоза животного не подтверждены.
Типы standard/fast/branded и коэффициенты явно синтетические. Fast определяется
по названию Сапсан/Ласточка, прочие provider-рейсы используют standard; branded —
явный параметр модели, не определяемый эвристикой по номеру поезда.

Демонстрационные часы, расстояние 650 км, цены, наличие классов — синтетика.
Инструмент не подтверждает наличие мест, реальный тариф РЖД или возможность покупки.
Изменение модели/seed меняет offer_id. Все данные читаются как UTF-8 из общего DATA_DIR.

```sh
make d6-check
make d6-demo
```

Провайдер: Яндекс Расписания, endpoint
https://api.rasp.yandex-net.ru/v3.0/search/ ; форма/поля сверены 27.10.2026 по
https://yandex.ru/dev/rasp/doc/ru/reference/schedule-point-point .
Ключ передаётся в Authorization, что поддерживает официальная документация.
Города c146/c213; выдача ограничена сопоставленными главными вокзалами.
Расписание проверяется по локальной дате, UTC-длительности и станциям; исключаются
пересадки и спальные классы у известных сидячих экспрессов. Повторные сегменты
не становятся повторными предложениями. Класс остаётся входом модели, не наличием мест.

HTTP-клиент инъецируется через TrainHttpClient (mode/get); D4 совместим, но не
является обязательным импортом. Provider mode не подменяется synthetic при
ошибке/пустом ответе. HTTP/JSON/структурные ошибки — ProviderResponseError;
ошибка кэша остаётся ошибкой кэша. В приложении фабрика реестра создаёт D4-клиент
и закрывает его при остановке. Переданный через `create_tools(..., train_http=...)`
клиент остаётся во владении вызывающего кода.
В репозитории yandex_search.synthetic.json — написанная вручную тестовая форма ответа,
не настоящая запись API. Доступ с настоящим ключом и актуальное расписание
этой проверкой не подтверждены. Настройки доступа:
https://yandex.ru/dev/rasp/doc/ru/concepts/access .

Основные тесты не зависят от D4; `test_trains_d4.py` проверяет D4 record/replay
на написанном вручную ответе через MockTransport. `test_chat_yandex.py` проверяет
весь HTTP/SSE-путь чата: запрос → реестр → Яндекс-адаптер → D4 → карточки поездов.
Это проверка интеграции и очистки секретов, а не проверка доступа к Яндексу.

## Подключение к чату без внешней модели

Настройки уже поддерживаются общим реестром:

```dotenv
LLM_PROVIDER=fake
TOOLS_MODE=real
FLIGHTS_MODE=synthetic
TRAINS_MODE=yandex
CACHE_MODE=replay
YANDEX_RASP_API_KEY=
YANDEX_CACHE_DIR=
```

По умолчанию `TRAINS_MODE=synthetic`: сеть и ключ не нужны. `yandex` требует
`TOOLS_MODE=real`. В `record`/`live` нужен `YANDEX_RASP_API_KEY`; для `replay`
существующего ответа ключ не нужен. Ключ хранится только на сервере в приватном
`.env` или переменной окружения, имеет тип SecretStr и не показывается в repr
настроек и сообщениях их валидации. Он передаётся только заголовком Authorization,
не в URL, карточки, SSE, логи или тело записанного ответа.

Пустой `YANDEX_CACHE_DIR` означает `DATA_DIR/cache/yandex/runtime`. В `record`
эта директория должна быть доступна для записи. `record` каждый раз обращается
к провайдеру и сохраняет очищенный ответ; `replay` читает только существующий
кэш; `live` обращается к провайдеру без записи. Автоматического обновления или
TTL здесь нет. Отсутствие записи, ошибка доступа или пустое расписание не
подменяются демонстрационными поездами.

Событие `tool_result` для `search_trains` содержит безопасные метаданные:
`source=yandex_timetable` только при непустом результате, `cache_mode`,
`schedule_quote_count`, `price_modelled=true`, `availability_confirmed=false`,
`class_availability_confirmed=false`, `price_scope=group_one_way`. При пустом
ответе `source=null`: настройка источника не объявляется полученной котировкой.
В режиме synthetic источник явно помечен как synthetic.

Даже с расписанием Яндекса `Train.is_synthetic=true`: цена всей группы,
детские тарифы, выбранный класс и возможность перевозки животного не подтверждены
поставщиком. Это поиск расписания с модельной ценой, не продажа билета.

Чтобы завершить живую проверку после получения ключа, нужно записать один ответ
для LED ↔ MOW на конкретную будущую дату, сверить станции и местные времена,
а затем воспроизвести тот же запрос в `replay` без ключа и сети. До этого этапа
нельзя заявлять, что рабочий доступ к API Яндекса проверен.

## Решение для текущей сдачи

Используем `TRAINS_MODE=synthetic`: это явные моки расписания и модельные цены,
без сети и ключа Яндекса. Такой режим подходит для демонстрации инструментов,
классов, состава группы и часовых поясов. Подключение реального Яндекса остаётся
отдельным этапом исходной D6, а текущий мок не называется проверенным API-доступом.
