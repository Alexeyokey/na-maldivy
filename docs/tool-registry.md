# Реестр D2/D3/D5/S4

После слияния D5 #54, D3 #55 и D2 #57 фабрика `create_tools(Settings(tools_mode="real"))`
предоставляет четыре инструмента: `search_flights`, `search_hotels`,
`suggest_destinations`, `get_transfer`. Все используют один `Settings.data_dir`
(переменная `DATA_DIR`, по умолчанию корневой `data/`), без сети и ключей.

`real` здесь означает реализации адаптеров вместо фиксированных заглушек D1.
У рейсов синтетические расписание и тариф, у отелей — коммерческие условия,
у S4 — тарифы и расписание. У D5 — источники справочных фактов и расчётная
длительность полёта; неизвестная цена возвращается как null. Это не живая выдача поставщиков.
Режим provider у D2 включается отдельно с инъекцией HTTP-клиента; фабрика не
создаёт сетевых клиентов и не управляет их жизненным циклом. D4 #56 совместим,
но не является обязательной зависимостью автономного реестра.

До слияния зависимостей `stub` работает как раньше, а `real` выдаёт явную ошибку
о недостающих реализациях. Сломанные импорты зависимостей не скрываются.
Поезда D6 и календарь D8 в `real` пока отсутствуют: они не подменяются заглушками.
`tool_specs(tools)` экспортирует только доступные в переданном реестре инструменты.

```python
from app.config import Settings
from app.tools.registry import create_tools, run_tool, tool_specs

tools = create_tools(Settings(tools_mode="real"))
flights = await run_tool("search_flights", {
    "origin": "SVO", "destination": "MLE", "departure_date": "2026-11-18",
}, tools=tools)
specs_for_llm = tool_specs(tools)
```

Для A2 нужно передать этот реестр и схемы в обработчик диалога. Этот PR меняет
фабрику инструментов, а не цикл агента, события интерфейса или сборку TripState.
Интеграционные проверки вызывают инструменты через D1-диспетчер, проверяют
общие ID отелей, S3/S5 и ночное ожидание гидросамолёта. В отдельной ветке PR
проверки полной сборки пропускаются до появления D2/D3; в общей сборке обязательны.
