# D1: контракты инструментов, черновик v0 для O1

Это предложение для встречи [O1 (#3)](https://github.com/ostrovok-hackathon-2026/na-maldivy/issues/3).
Контракты ещё не утверждены командой. В черновике готовы типы, заглушки и реестр D1.
Настоящие источники появятся в D2/D3/D5/D6/S4. Подключение инструментов к `/api/chat` относится к A2.

## Общие правила

- Идентификаторы — строки. Цены — неотрицательные целые рубли, без неявного округления дробных значений.
- `Place`: `iata`, название, координаты, IANA `timezone`. В запросах допускаются IATA городов и аэропортов.
- `Travelers`: `adults`, `children_ages` (0–17 лет), `pets`. Должен быть хотя бы один взрослый.
- Перелёт и поезд ищутся в одну сторону. Обратное направление — отдельный запрос.
- `price_rub` перелёта/поезда — за всех путешественников в одну сторону. Багаж перелёта лежит отдельно
  в `baggage_price_rub` и тоже указан за всю группу.
- `HotelOffer.price_rub` — за всю группу и весь интервал `[check_in, check_out)`, без трансфера.
- `Transfer.price_rub` — за всю группу и весь маршрут; повторно умножать на число пассажиров не нужно.
- Оценка стоимости направления включает перелёт туда и обратно и отель на `nights` за всю группу.
  Это ориентир для подбора, а не цена готового варианта с багажом/визой/трансфером.
- `DayPrice.price_rub` — минимальная цена перелёта в одну сторону за всю группу, без отеля.
- `departure_at`, `arrival_at`, `pickup_at` — ISO 8601 с UTC-смещением местной точки. Наивные даты-время
  отклоняются. Порядок отправления/прибытия проверяется по абсолютному времени.
- Календарные даты — `YYYY-MM-DD`, месяц календаря цен — `YYYY-MM`.
- Все ответы D1 помечены `is_synthetic=true`. Названия, цены, климат и правила заглушек не являются
  проверенными предложениями или справочной информацией о реальных объектах.
- Неизвестные поля входа отклоняются: опечатка аргумента не должна незаметно менять поиск.

## Инструменты

| Имя | Вход | Выход | Основные аргументы |
|---|---|---|---|
| `search_flights` | `FlightSearch` | `list[Flight]` | `origin`, `destination`, `departure_date`, `travelers`, `direct_only`, `max_price_rub` |
| `search_hotels` | `HotelSearch` | `list[HotelOffer]` | `destination`, `check_in`, `check_out`, `travelers`, `min_stars`, `refundable_only`, `max_price_rub` |
| `search_trains` | `TrainSearch` | `list[Train]` | `origin`, `destination`, `departure_date`, `travelers`, `seat_class` |
| `get_transfer` | `TransferQuery` | `Transfer` | `origin` и `destination` как `Place`, `pickup_at`, `travelers` |
| `suggest_destinations` | `DestinationQuery` | `list[Destination]` | `month`, `origin`, `travelers`, `nights`, `budget_rub`, `min_water_temperature_c`, `visa_free_only` |
| `price_calendar` | `PriceCalendarQuery` | `list[DayPrice]` | `origin`, `destination`, `month`, `travelers` |

Варианты `seat_class`: `platzkart`, `coupe`, `sv`, `seated`.
Отель содержит правила детей/животных, возвратность, местное время заезда/выезда, возможную цену раннего
заезда и время закрытия ресепшена (`null` — круглосуточно). Это входы для будущего валидатора S5.

## Использование без агента

Из каталога `backend`:

```python
import asyncio
from app.config import Settings
from app.tools import create_tools, run_tool, tool_specs

async def main():
    tools = create_tools(Settings(tools_mode="stub", llm_provider="fake"))
    flights = await run_tool("search_flights", {
        "origin": "SVO",
        "destination": "AYT",
        "departure_date": "2026-11-18",
        "travelers": {"adults": 2, "children_ages": [5]},
    }, tools=tools)
    print(tools["search_flights"].output_adapter.dump_json(flights).decode())
    # Эти спецификации принимает существующий LLMClient.complete(..., tools=...).
    specs = tool_specs(tools)
    print([spec.name for spec in specs])

asyncio.run(main())
```

`Tool` описывает `name`, `description`, `input_model`, `output_adapter` и `async run(input)`.
`run_tool` проверяет JSON-аргументы через входную pydantic-модель, затем проверяет результат через
`output_adapter`. Для прямого вызова `tool.run()` сначала создайте экземпляр входной модели.

`TOOLS` — готовый реестр заглушек без чтения `.env`. Для приложения используйте `create_tools(settings)`:
он учитывает `TOOLS_MODE`. Режим `real` пока явно выдаёт `NotImplementedError`, вместо подмены настоящих
ответов синтетическими. A2 должен передавать полученный реестр в диспетчер и в `tool_specs`.

Ошибки границы: неизвестное имя — `KeyError`, неверные аргументы или ответ — `ValidationError`.
Перевод этих ошибок в понятный ответ пользователю относится к A2.

## Заглушки и воспроизводимость

Заглушки не используют сеть, ключи, LLM или текущее время. Одинаковый запрос возвращает одинаковые
данные; вызовы возвращают новые объекты, которые можно изменять, не портя следующие ответы.
Поддерживаемые маршруты и тестовые ловушки описаны в `backend/app/tools/stubs.py` и проверены тестами.
Пустой результат для неизвестного направления — нормальное поведение. Неподдерживаемый трансфер
вызывает `ValueError`: у его контракта один результат, а не список.

Демо-каталог:

- Перелёты: SVO/MOW или LED ↔ AYT, DXB, MLE. MOW в авиапоиске означает SVO.
  Два прямых рейса в день: 09:00 и 23:30. Например, SVO 18 ноября 23:30+03:00 → DXB 19 ноября 06:00+04:00.
- Отели: четыре синтетических предложения на направление. Есть невозвратный бюджетный отель
  с ресепшеном до 22:00, семейный, adults-only и премиальный. Фильтры учитывают детей и животных.
- Поезда: Москва ↔ Петербург. Здесь SVO преобразуется в город MOW; у LED используются городские координаты.
- Трансферы: только между точными точками каталога в одной демо-локации либо SVO ↔ MOW.
  Для аэропорт → отель берите `Place` из ответа перелёта и предложения отеля, как в тестовых примерах.
- Направления: три синтетических профиля с климатом по 12 месяцам. Календарь цен согласован
  с минимальными ценами `search_flights` и покрывает все дни выбранного месяца.

## JSON Schema и проверки

```bash
make schemas     # обновить contracts/schema/tools.json
make check-fast  # линтер и тесты, включая проверку актуальности выгрузки
make check       # дополнительно Docker и HTTP smoke, если Docker запущен
```

`contracts/schema/tools.json` — общий JSON Schema с разделяемыми `$defs`. В `properties` лежат
шесть инструментов, у каждого — схемы `input` и `output`. Объект вида
`{"search_flights": {"input": ..., "output": ...}, ...}` можно целиком проверить этой схемой.
Это описание и формат тестовых примеров, а не новый HTTP endpoint.

Для LLM используется только входная схема каждого инструмента, которую `tool_specs()` получает
непосредственно из `input_model.model_json_schema()`. Тест с подставным HTTP-сервером проверяет передачу
этих схем через существующий OpenAI-совместимый клиент; внешняя модель для теста не вызывается.

## Решения для O1

1. Утвердить шесть имён инструментов и поля запросов/ответов.
2. Согласовать `Travelers` с полями TripState (R1), включая возраст детей и животных.
3. Подтвердить единицы цен и отдельный учёт багажа с R2/S1.
4. Подтвердить работу с IATA городов/аэропортов и локальным временем с D2/S3.
5. После договорённостей обновить модели, выгрузку и примеры вместе; затем подготовить PR D1.
