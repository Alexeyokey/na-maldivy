# D3: общий каталог отелей и синтетические предложения

Задача [#9](https://github.com/ostrovok-hackathon-2026/na-maldivy/issues/9).
Поиск использует контракты D1 v0.1 из
[PR #50](https://github.com/ostrovok-hackathon-2026/na-maldivy/pull/50).
Пока D1 не влит, PR D3 основан на его ветке; порядок слияния — D1, затем D3.

## Каталог и происхождение

`data/hotels/osm_hotels.json` — единый сохранённый список D3/S4:

| Направление | Отелей D3 | Отелей S4 | Совпадают |
|---|---:|---:|---:|
| Анталья, AYT | 20 | 20 | 20 |
| Дубай, DXB | 20 | 20 | 20 |
| Мальдивы, MLE | 20 | 20 | 20 |

`scripts/fetch_hotels.py` без сети проецирует этот список в `catalog.json`,
`id_aliases.json` и `sources.json`. Manifest фиксирует SHA256 исходного файла.
Совпадают физические ID, названия, координаты и нормализованные звёзды.
У каждого объекта есть ссылка OSM. Исходный снимок S4 нормализован: в нём
нет оригинальных тегов звёзд, версий и временных меток объектов; эти поля
в D3 остаются `null`. Координаты островного курорта не означают дорожную связь с MLE.

Название, координаты и заполненные звёзды — справочные данные участников OSM,
а не проверка действующего поставщика или актуальной категории отеля.

[ODbL 1.0](https://opendatacommons.org/licenses/odbl/1-0/).
При показе фактов сохраняйте атрибуцию и ссылку на
[OpenStreetMap](https://www.openstreetmap.org/copyright).

## Поиск и правила

`backend/app/tools/hotels.py` предоставляет `HotelSearchTool`, `search_hotels`
и подробный `search_hotel_results`. Они работают с локальными файлами.

```python
from app.contracts.tools import HotelSearch
from app.tools.hotels import HotelSearchTool

offers = await HotelSearchTool().run(HotelSearch(
    destination="DXB", check_in="2026-11-18", check_out="2026-11-25",
    travelers={"adults": 2, "children_ages": [5]}, refundable_only=True,
))
```

`hotel_id = osm:<type>/<id>` обозначает физический объект, `offer_id` — конкретный
запрос и версию тарифа. Старое двоеточие принимается как lookup alias активного ID;
ответы всегда используют `/`. Идентификатор предложения не является токеном поставщика.

**Цены, наличие, рейтинг, удобства, условия детей/животных, возвратность, часы
заселения, ранний заезд и расстояние до пляжа синтетические.** Они не описывают
реальные правила названного отеля. Каждое предложение помечено `is_synthetic=true`
и отдельным notice; имя остаётся чистым, подробный результат сохраняет исходные факты
отдельно от demo overlay. Тарифы `synthetic-hotel-v3` воспроизводятся из ID и даты.

Цена — рубли **за всю группу, все комнаты и все ночи**. Вместимость комнаты —
до двух взрослых и четырёх платных гостей; младенцы до двух лет не добавляют комнат.
Доплата 1000 ₽ за питомца включена один раз за весь срок. Ранний заезд, если
доступен, имеет отдельную цену за все комнаты. Повторно умножать суммы на людей
или ночи нельзя.

Жёсткие фильтры исключают adults-only с детьми, запрет животных, невозвратный
тариф при `refundable_only`, превышение бюджета, недостаточные/неизвестные
звёзды и закрытые даты синтетического наличия. Неизвестное направление даёт `[]`.
Пять воспроизводимых ловушек описаны в [data/traps.md](../data/traps.md).

## Совместимость и проверки

```bash
cd backend
uv sync --locked
cd ..
make d3-data          # пересобрать D3 из сохранённого S4, затем demo-правила
make d3-check         # весь backend, Ruff, каталог/правила, схемы и примеры D1
make d3-compat-check  # отдельный набор D3/S4
```

После установки зависимостей эти команды не обращаются к сети или LLM.
`scripts/fetch_hotels.py --check` и `scripts/build_hotel_rules.py --check`
сравнивают сохранённые результаты без записи. Они проверяются и в `d3-check`.
Генератор правил на стандартной библиотеке отмечает результат как
`synthetic-hotel-rules-v3`; D7 и провайдеры для него не нужны.

При выделении PR успешно прошли `make d3-check` (540 тестов, Ruff,
воспроизводимость данных, схемы и примеры) и `make d3-compat-check` (244 теста).
Compose-конфигурация корректна; Docker daemon недоступен, поэтому сборка образа
и Docker smoke не проверены.

Тесты используют настоящие выходы поиска D3 и адаптера S4, таймлайн S3 и валидатор
S5; рейсы задаются синтетическими D1-фикстурами. Для всех 60 отелей проверяются
дневное/ночное прибытие, идентичность точек, цены всей группы и расписание.
Отдельно проверяются дети/животные, неизвестные часы отеля и ночной прилёт
в 23:40 к курорту с гидросамолётом с 06:00. Неизвестный ID и неверный аэропорт
остаются ошибками `UnsupportedTransfer`.

136 вариантов S4 и 40 OSRM-маршрутов сохранены. Пересборка S4 в тестовой папке
воспроизводит опубликованную базу; отсутствие дорожного маршрута AYT/DXB,
неверный аэропорт, лишние маршруты и дубли останавливают сборку.
Время выбранного S4-маршрута передаётся в S3/S5; 120 минут из D3 `far_transfer`
остаются отдельной фикстурой и не подменяют маршрут.

## Обновление и границы

Явное сетевое обновление выполняет S4: из `backend/` запустить
`uv run python scripts/build_transfers.py fetch`, затем `build`.
После этого выполнить `make d3-data`, проверить изменившиеся маршруты/эталоны
и запустить `make d3-check`. Отдельного выбора отелей в D3 больше нет.

Compose монтирует `./data` в `/data:ro` и задаёт `DATA_DIR`.
Образ сам по себе данные не содержит. Проверка Compose не подтверждает сборку Docker.

Реализация покрывает MVP «20+ отелей на направление с правилами отмены, для детей
и животных». LiteAPI не подключён; коммерческие данные и доступность не подтверждены.
Развёрнутые тарифы отмены по дням, типы номеров, кроватки и возрастные правила
остаются расширением. D7-профили отзывов ведутся отдельно. Реестр по умолчанию
сохраняет D1-заглушки; подключение к A2/чату и согласование O1 здесь не завершаются.

## Уточнения после review

Имя `HotelOffer.name` совпадает с OSM-названием; синтетичность передаётся полем
`is_synthetic` и отдельным notice. Все JSON-файлы читаются как UTF-8.
Единый `DATA_DIR` задаёт корень каталога, правил и S4.
Демонстрационная модель семейного номера v3 допускает до двух взрослых и четырёх
платных гостей: `rooms = max(ceil(adults/2), ceil((adults + children_age_2_plus)/4))`.
Младенцы младше двух лет не увеличивают число номеров, но по-прежнему не проходят
фильтр adults-only. Это синтетическое правило, фактическая вместимость не установлена.
Семья 2+2 теперь получает один номер; четыре взрослых — два. Изменение версии
меняет offer_id, сохраняя hotel_id и исходные OSM-факты. Реестр — отдельный зависимый PR.
