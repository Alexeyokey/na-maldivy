# Aviasales → D4 → поиск в чате

`POST /api/chat` использует авиапоиск из общего реестра. Строгий режим ниже —
`FLIGHTS_MODE=aviasales`; отдельный `demo` описан в конце документа. При явном выборе
Aviasales инструмент получает котировки через `CachedHttpClient` D4; календарь
D8 использует тот же экземпляр авиапоиска. Ошибки API, отсутствие записи или
подходящей котировки не переключают поиск на синтетические рейсы.

## Локальная настройка

В приватном `.env` задайте:

```dotenv
TOOLS_MODE=real
FLIGHTS_MODE=aviasales
CACHE_MODE=record
LLM_PROVIDER=fake
```

Ключ вводится отдельно в `AVIASALES_API_TOKEN` этого файла, без отправки в чат,
браузер, командную строку или Git. Образец `.env.example` содержит пустое поле.
`SecretStr` скрывает значение в представлении настроек; ошибки валидации
настроек не печатают входные значения. Для нового локального `.env` установите
права `chmod 600 .env`.

`LLM_PROVIDER=fake` оставляет разбор сообщения правилами и ответы по шаблонам;
источник цен выбирается независимо. Для LLM нужны отдельные настройки из
`.env.example`. Проверка ниже не проверяет качество внешней LLM.

Из корня репозитория после установки зависимостей:

```bash
cd backend
uv run --locked --offline uvicorn app.main:create_app --factory --port 8000
```

Запрос к запущенному серверу:

```bash
curl --no-buffer http://localhost:8000/api/chat \
  -H 'Content-Type: application/json' \
  -d '{"message":"Из Москвы в Анталью 18 ноября 2026 на неделю вдвоём"}'
```

Дата выше — воспроизводимый пример проверки, а не актуальная рекомендация поездки.
Автоматическое сопоставление `MOW → SVO` ограничивает поиск Шереметьево.

## Режимы и расположение кэша

| `CACHE_MODE` | Поведение авиапоиска |
|---|---|
| `record` | Каждый запрос идёт в API и заменяет соответствующую запись D4. Нужен ключ. |
| `replay` | Только сохранённые ответы; ключ не нужен. Нет записи — ошибка без сетевого обхода. |
| `live` | Запрос в API без чтения и записи кэша. Нужен ключ. |

По умолчанию файлы находятся в `DATA_DIR/cache/aviasales/runtime`;
`AVIASALES_CACHE_DIR` позволяет выбрать другую записываемую директорию.
Автоматического TTL или перехода `replay → record` нет. После изменения режима
перезапустите backend. Для офлайн-демо выберите `replay` после успешного `record`.
В режиме `synthetic` настройки и ключ Aviasales не используются.

`data/cache/aviasales/` исключён из Git: runtime-ответы и локальные отчёты
не публикуются автоматически. Другой checkout не получит этот приватный кэш вместе с кодом.
Для собственного пути вне этой директории настройте исключение самостоятельно.
Собственный HTTP-клиент реестра закрывается при завершении приложения;
клиент, переданный через `flight_http`, закрывает вызывающий код.

Для переносимого демо отдельно подготовлен публичный снимок
[`data/demo/aviasales`](../data/demo/aviasales/README.md): **47 очищенных записей**
с происхождением и SHA256. Есть основные и соседние даты Антальи, Мальдив и
запросов Дубая. Ответы SVO → DXB содержат DWC и исключаются при поиске DXB;
для обратного DXB → SVO подходящие записи есть не на каждый день.
Подробное покрытие — в README снимка. Проверка: `make demo-cache-check`.

Для локального запуска без ключа выберите `CACHE_MODE=replay` и
`AVIASALES_CACHE_DIR=<абсолютный путь к data/demo/aviasales>`.
При новой записи используйте отдельный runtime-кэш, сохраняя снимок демо неизменным.

`make demo-up` объединяет Compose с `docker-compose.demo.yml`: образ
`backend/Dockerfile.demo` включает публичные данные, без bind-mount папки
компьютера; записываемый именованный том `/state` отделён от них.
Сеть `internal`, ключи и внешняя модель отключены. Первичная сборка требует
доступа к образам и зависимостям; runtime-проверка выполняется без внешней сети.
Обычный Compose оставляет `/data:ro` и `/state` для `record`; там
`AVIASALES_CACHE_DIR=/state/aviasales`, а путь с компьютера не переносится.

## Что получает агент и пользователь

В каждом `Flight.price_source` доступны только публичные поля:

- `provider=aviasales_data_api`, исходная `seat_price_rub`, валюта RUB;
- `cache_mode`, `cache_hit`, `recorded_at` — время записи D4, а не время последнего поиска тарифа у Aviasales;
- признаки расчётной длительности, цены группы и багажа.

SSE `tool_result` содержит источник и эти метаданные; карточки `options` сохраняют
`price_source` у обоих перелётов. Ответ по шаблону называет исходную котировку
за одно место и дату записи. Инструкция LLM требует сохранять это различие.
В `live` время записи отсутствует, потому что запись D4 не создаётся.

Котировка Data API — наблюдение из кэша поисков провайдера. Наличие мест и
окончательная стоимость покупки не подтверждены. Цена всей группы, младенцы,
питомцы и багаж вычисляются демонстрационной моделью D2; отель и трансфер тоже
расчётные. Поэтому `is_synthetic=true` у `Flight` сохранён даже при настоящей
исходной котировке. `price_source` позволяет отличить её от полностью
синтетического рейса. Итог варианта покрывает только показанные компоненты;
обратный трансфер, виза и прочие доплаты не оценены.

Ключ передаётся провайдеру только заголовком `X-Access-Token`. D4 исключает
секреты из идентичности запроса и удаляет отражённые значения из ответа.
При ошибке инструмента агент пишет в лог только имя инструмента и класс ошибки,
без исходного текста исключения, заголовков или тела ответа.

## Явный смешанный демо-режим

`FLIGHTS_MODE=demo` требует `TOOLS_MODE=real`, `CACHE_MODE=replay`; ключ игнорируется.
Сначала ищется подходящая реальная запись D4. При CacheMiss или корректном ответе
без подходящих котировок генерируется мок с `demo_source.kind=deterministic_mock`.
У него нет `price_source` Aviasales. Существующие дорогие котировки, повреждённый
кэш и ошибки провайдера не заменяются более дешёвым мок-рейсом.

У каждого плеча отдельно видны `demo_source` и исходная котировка, если она есть.
Метки проходят в карточки, текст, D8 и ваучер. При участии мока сравнение дат
получает `savings_kind=demonstration_estimate`; это расчётная демонстрация.
Режим включён в Docker-демо и переносимый пакет. Строгий `aviasales` остаётся
доступным без автоматической подмены источника.
