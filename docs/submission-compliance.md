# Требования сдачи и состояние передачи

Документ отделяет техническую готовность от финальной сдачи. Основание —
правила хакатона, переданные владельцем проекта. Дата подготовки: **29.10.2026**.
Актуальный путь запуска — [README](../README.md), действия судьи —
[проверка за 5–10 минут](judge-guide.md).

**Тег `submission` намеренно не создаётся по прямому указанию владельца.**
Точный дедлайн не предоставлен; автоматическая финализация не настроена.
Публичной ссылки на обязательное демо-видео пока нет.

## Что остаётся для сдачи

| Действие | Состояние |
|---|---|
| Выбрать и включить окончательную проверенную сборку в `main` | Базовая Docker-сборка включена через PR #64. Последующие улучшения нужно оценивать по фактически включённому коммиту; незамерженный PR не входит в обычный `git clone`. |
| Повторить запуск именно сдаваемого `main` | После последнего изменения: новая копия, `.env.example` → `.env`, обычный `docker compose up --build`, путь из руководства судьи и документы. Исторические отчёты не заменяют эту проверку. |
| Записать демо-видео и разместить публичную ссылку в README | **Не выполнено.** Есть [сценарий записи](video-recording.md). Ссылка должна открываться без аккаунта, в том числе в инкогнито. |
| Сохранить доступ жюри к командному GitHub-репозиторию | Репозиторий командной организации; доступ проверяется через организацию. Нельзя требовать доступ к частному реестру, личной подписке или паролю сайта для локального запуска. |
| Поставить `submission` на последнем сдаваемом коммите основной ветки | **Отложено владельцем. Не выполнять до отдельного указания.** |

Скриншоты, размещённый сайт, HTTP-трассы и слайды не заменяют обязательное
видео. Отсутствие тега и видео нельзя объявлять завершённой сдачей даже при
успешных тестах.

## Технический пакет

Здесь описан стандартный граф `docker-compose.yml`, а не отдельные
разработческие/серверные Compose-профили.

| Требование | Реализация / как проверить |
|---|---|
| Один командный репозиторий | `ostrovok-hackathon-2026/na-maldivy`; код и данные для стандартного запуска находятся в нём. |
| `README.md`, `docker-compose.yml`, Dockerfile, `.env.example` | Все есть. Активные Dockerfile: `backend/Dockerfile.demo` и `frontend/Dockerfile`. |
| Запуск одной командой после копирования `.env` | `docker compose up --build` из корня; Python, Node.js, модель и ключи на машине жюри не требуются. |
| Приложение на 8080 | `app` слушает внутри 8080, наружу `8080:8080`. Backend `agent:8000` остаётся внутри Compose-сети. |
| Все зависимости в Docker | Два сервиса: `agent` и `app`. SQLite встроена в Python; отдельная БД/Redis не нужны. |
| Автоматические данные / миграции | Публичные каталоги включены в backend-образ. SQLite создаёт таблицы при запуске в именованном томе `agent-state`. |
| Публичные зависимости | Python lock использует публичный PyPI; frontend не имеет npm-зависимостей. Стандартная сборка не требует закрытого контейнерного реестра. |
| Закреплённые версии | Базовые образы Python/Node/uv имеют версии и SHA256; Python-пакеты закреплены в `backend/uv.lock`. |
| Multi-stage и non-root | Оба активных Dockerfile разделяют сборку и runtime; финальные процессы UID/GID `1000:1000`. `uv`, pytest, Ruff и компиляторы не устанавливаются в backend runtime. |
| Health и готовность | `/health`, Dockerfile HEALTHCHECK, Compose healthcheck и `depends_on: service_healthy`. |
| Apple Silicon | Явная `platform: linux/amd64` у обоих сервисов. На ARM Docker должна быть включена эмуляция. |
| Секреты | Пример содержит пустые ключи. `.env`, auth/runtime-файлы и артефакты исключены из Git. Токены не должны попадать в UI, логи, отчёты или Docker-слои. |
| Логи | Основные процессы пишут stdout/stderr, доступны через `docker compose logs app agent`. Backend не журналирует приватные capability URL в access log. |
| Ресурсы | README: 2 CPU, 2 ГБ RAM, 2 ГБ диска сверх Docker. Runtime caps: 512 MiB/1 CPU для `agent`, 128 MiB/0,5 CPU для `app`; сборке может понадобиться больше. |
| Без тяжёлой локальной модели | Стандартное демо выбирает `LLM_PROVIDER=fake`. Внешний OpenAI-совместимый API подключается отдельно. Веса моделей для запуска не нужны. |
| Время развёртывания | На `c4f6b3c`: 6,684 с no-cache сборка + 8,160 с до health, Apple M3 / 16 GiB. Базовые слои уже были на машине; полностью холодный Docker Engine не измерялся. См. новый отчёт. |
| CI | Workflow есть; статус конкретного запуска проверяется отдельно. Локальная проверка — `make check`. Наличие workflow не означает успешный CI на текущем коммите. |

## Повторить проверку

Основная приёмка — пользовательский путь в [руководстве судьи](judge-guide.md).
Он не требует установки инструментов разработчика. Внутри уже запущенного
контейнера доступен автоматический HTTP-проход трёх направлений:

```bash
docker compose exec -T agent python /app/scripts/check_running_three_destinations.py \
  --base-url http://app:8080 \
  --context /state/judge-three-private.json --output /state/judge-three-report.json
```

Команды проверки сохранения после restart и границы отчёта — в
[руководстве](judge-guide.md#необязательные-технические-проверки). Это не
браузерный прогон. Context приватный и остаётся только в локальном томе;
stdout/report безопасны для передачи. Запуск создаёт вымышленные демо-заказы,
не реальные брони.

Дополнительная read-only проверка конфигурации на машине с Python 3.11+:

```bash
python3 scripts/check_submission_package.py
# Также проверить уже запущенные UI и /health на стандартном порту:
python3 scripts/check_submission_package.py --base-url http://localhost:8080
```

Проверяющий скрипт не выполняет сборку или запуск. Он разрешает только
`.env.example`, не выводит приватную `.env` и полный Compose config. Результат
имеет `scope=default_docker_package` и `handoff_certified=false`: зелёный
технический отчёт не доказывает наличие видео, перенос кода в `main` или тег.

Для разработки `make check` запускает Ruff, backend/frontend-тесты и отдельный
Docker smoke. Для него нужны Python/uv, Node.js и Docker; они не являются
дополнительным условием обычного Docker-запуска приложения.

## Проверки и их границы

Текущий проверенный код: **`c4f6b3c`**, 29.10.2026 МСК.
[Новый пакет доказательств](../eval/reports/judge-readiness-2026-10-29/README.md):
1354 backend + 181 UI + 11 HTTP-тестов, стандартный Docker smoke, новый clone
из GitHub с `.env.example`, анонимная сборка публичных зависимостей, три
направления, будущие даты, сохранение заказов/документов после restart и
отдельная работа в Docker internal-сети. Браузерный проход и его границы
зафиксированы в [local-ui.json](../eval/reports/judge-readiness-2026-10-29/local-ui.json).

Исторические свидетельства сохранены в
[`eval/reports/submission-compliance-2026-10-28/`](../eval/reports/submission-compliance-2026-10-28/).
На архиве `1419c92` были проверены стандартная команда запуска, UI/health на
8080 и `make check`. На `1c1a023` повторены чистая сборка, три направления,
перезапуск и браузерное восстановление оплаченного заказа/документов.
Эти отчёты подтверждают только обозначенные там версии. Счётчики старых тестов,
прежние ветки и старые порты не являются метрикой текущего коммита.

После включения изменений в `main` перед финальной сдачей нужно повторить
проверку основной ветки, сохранив её SHA. Критерии:

- UI и `/health` доступны через единственную стандартную точку 8080.
- Анталья, Дубай и Мальдивы дают ожидаемые источники для каждого плеча;
  синтетические данные не выдаются за текущие котировки.
- Изменение направления/пассажиров обновляет карточки и панель одновременно.
- Работают отказ и успех демо-оплаты, идемпотентное повторение, HTML-ваучер и `.ics`.
- После перезапуска `agent` оплаченный заказ и содержимое документов сохранены;
  незавершённая поисковая сессия честно предлагает новый поиск.
- Пакет не зависит от локального `.env`, личной авторизации, runtime-кэшей,
  `artifacts/`, приватного сайта или предварительно установленной модели.

## Ограничения, которые нужно сохранить видимыми

1. Локальное демо использует правила и шаблоны. Оно не подтверждает качество
   выбранной внешней модели и настоящий LLM-прогон извлечения D7.
2. Авиакотировки — сохранённые наблюдения от 28.10.2026; отсутствующие данные в
   отдельном `demo`-режиме дополняются подписанными моками. Текущая цена и
   наличие мест не подтверждаются.
3. Стоимость группы, багаж, отели, трансферы, отзывы и поезда расчётные или
   синтетические. Обратный трансфер, визы и другие обязательные доплаты не оценены.
4. Платёж имитируется. Реальная оплата, выписка билетов и бронирование у
   поставщиков отсутствуют. Для поездов реализован поиск, не оформление билетов.
5. Настоящий доступ к Яндекс Расписаниям не проверен. Поезда работают без ключа
   на синтетических данных.
6. Незавершённые серверные сессии хранятся в памяти. Заказы сохраняются в SQLite;
   браузерные ссылки доступа принадлежат исходной вкладке.
7. Исходный бюджетный критерий `u2-03` не проходит при 150 000 ₽. Агент корректно
   отказывает, поскольку известные расходы выше бюджета; это не скрывается под
   успешной оценкой. [Разбор](../eval/reports/u2-budget-feasibility.md).

Данные и их атрибуции: [инвентарь](data-inventory.md),
[`data/ATTRIBUTION.md`](../data/ATTRIBUTION.md). В корне нет общей лицензии
собственного кода: это не переданное обязательное условие сдачи, а выбор команды.
Лицензии данных и сторонних компонентов действуют отдельно.
