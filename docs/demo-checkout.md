# S1: сохраняемая демонстрационная корзина без внешней модели

Эта реализация завершает backend-путь «выбранный вариант → данные путешественников → тестовая оплата → заказ → ваучер и календарь». Она работает с разбором правил и шаблонными ответами; внешняя LLM и банковские ключи не нужны.

**Деньги не списываются, билеты не выписываются, отель и трансферы не бронируются.** Ваучер и события календаря явно помечены `ДЕМО`. Данные карты, PAN и CVV в API отсутствуют. На защите используйте вымышленные имена и даты рождения.

## Путь через HTTP

1. Через `/api/chat` найдите поездку, выберите вариант и подтвердите переход к оформлению. Подтверждение создаёт корзину, а не оплаченный заказ. Альтернатива для интеграции: `POST /api/checkout/carts` с `session_id`, `option` и актуальной `version` из сессии.
2. `PUT /api/checkout/carts/{cart_id}/travelers` принимает `session_id` и `travelers`: список объектов `full_name`, `birth_date` (`YYYY-MM-DD`). Количество взрослых и возраст каждого ребёнка на дату вылета должны совпасть с брифом. Паспортные данные не нужны.
3. `POST /api/checkout/carts/{cart_id}/pay` принимает:

   ```json
   {
     "session_id": "идентификатор из done",
     "outcome": "approved",
     "idempotency_key": "demo-payment-001",
     "acknowledge_demo": true,
     "acknowledge_unpriced": true
   }
   ```

   `outcome: "declined"` воспроизводит отказ: заказ не появляется, можно повторить с новым ключом и `approved`. Повтор запроса с тем же ключом возвращает прежний результат. Замена исхода под тем же ключом запрещена. Параллельные успешные запросы создают один заказ на корзину.
4. `GET /api/checkout/orders/{order_id}` восстанавливает оплаченный демо-заказ, в том числе после перезапуска сервера.
5. `GET /api/checkout/orders/{order_id}/voucher` скачивает HTML-ваучер; `/calendar.ics` — календарь перелётов и проживания. Для всех GET передайте `X-Session-ID: <session_id>`; идентификатор доступа не помещается в URL. Корзина читается через `GET /api/checkout/carts/{cart_id}` с тем же заголовком.

Ответы checkout имеют `Cache-Control: no-store`. Идентификатор сессии служит демонстрационным capability доступа; это не полноценная система пользователей и авторизации. Пути `/api/checkout/...` — локальная реализация демо, а не утверждение, что контракт O1 для `/api/cart` и `/api/orders` согласован.

## Что проверяет backend

Цена и состав берутся из выбранного варианта **на сервере**, клиент их не присылает. Корзина сохраняет отдельный снимок варианта и состава группы. Перед заполнением и оплатой проверяются версия брифа, актуальность, выбранный вариант и отпечаток состава: изменение условий или скрытая замена отеля требуют новой корзины.

Изменение корзины, данных и оплата используют тот же замок сессии, что и ход чата: сохранение копии диалога не может затереть результат оплаты. Повтор старого успешного запроса после изменения брифа возвращает исторический заказ, сохраняя состояние нового поиска.

`can_confirm` должен быть именно `true`, `validation_status` — `checked`; критические проблемы, неизвестные суммы, несовпадение суммы компонентов, время без часового пояса, противоречивые даты и неподтверждённые условия проживания с детьми/животными блокируют оформление.

Сумма относится к показанным компонентам: оба перелёта, багаж туда и обратно, проживание и трансфер в отель. Обратный трансфер, визы и прочие обязательные расходы остаются непосчитанными; для оплаты демо нужно явно подтвердить это. Реальная котировка Aviasales также не подтверждает наличие мест.

## Сохранение и календарь

`CheckoutService(db_path)` использует отдельную приватную SQLite-базу с режимом файла `0600`. Заказы и имена не попадают в D4, общие данные, переносимый публичный кэш или исходники. На каждый запрос открывается отдельное соединение; записи и повторы оплаты защищены транзакцией `BEGIN IMMEDIATE` и уникальностью заказа по корзине. Снимок оплаченного заказа неизменяем.

Готовые заказы читаются после перезапуска по номеру заказа и заголовку сессии. Незавершённая корзина после потери диалоговой сессии доступна для чтения, но для продолжения требуется повторный поиск: восстановление всего состояния агента в БД пока отдельно не реализовано.

В `.ics` перелёты переводятся из исходных смещений в UTC с `Z`; переход через полночь сохраняет правильную дату. Проживание — событие на даты с исключительным `DTEND`, без выдуманного времени заезда. Все события имеют `STATUS:TENTATIVE`, стабильные UID и предупреждение о демо; строки корректно переносятся по ограничению 75 октетов.

## Проверка

`backend/tests/test_demo_checkout.py` проверяет успешный путь, отказ и повтор, параллельную оплату без дублей, сохранение после перезапуска, несоответствие состава группы, устаревание/подмену варианта, запрет клиентских цен и карточных полей, недоступность чужой сессии, HTML-экранирование и календарь со сменой суток при переводе в UTC. Это backend-проверка; готовность клиентского интерфейса ей не утверждается.
